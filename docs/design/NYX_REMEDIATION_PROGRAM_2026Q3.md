# Nyx 工程化整改计划（2026 Q3）

**状态：** Active  
**开始日期：** 2026-07-31  
**目标：** 将项目从研究原型提升为可验证、可维护、可审计的授权演练平台。  
**非目标：** 不把未经验证的实验能力计入产品能力；不以功能数量替代可靠性、协作体验或合规性。

---

## 1. 成功定义

Nyx 是否达到下一阶段，不以代码行数或命令数判断，而必须同时满足：

1. **可用：** 支持范围内的完整工作流在隔离测试环境可重复通过。
2. **可诊断：** 失败能够关联到版本、操作者、配置、日志和明确的错误类别。
3. **可维护：** 核心模块边界清晰；接口、配置和数据迁移有兼容性策略。
4. **可协作：** 多操作者可了解资产、任务、证据、交接和决策历史。
5. **可交付：** 每个发布包均有可追溯构建、测试记录、支持矩阵和回退方案。

能力状态统一使用：`已交付`、`受限交付`、`实验性`、`规划中`。只有通过本计划所定义验收门的能力可标记为“已交付”。

## 2. 当前事实基线

本计划的初始事实来源为：

- `docs/audits/AUTHORITATIVE_FACTS_2026-07-18.md`
- `docs/audits/ANTI_HUMAN_AUDIT_2026-07-23.md`
- `docs/design/ROADMAP_2026-2027.md`
- 当前分支及 CI 的实际测试结果

基线审计已确认：服务端、协议和 UI 有较好基础；但若干关键实现仍处于未接线、未完成或仅有局部测试的状态。当前工作区中与传输可靠性和错误表达相关的未提交修改，必须保持原子、完成评审和验证后再进入主线，不能与本计划中其他整改混合提交。

## 3. 工作流与发布门禁

### 3.1 四层测试门禁

| 层级 | 内容 | 合并 / 发布要求 |
|---|---|---|
| L1 快速检查 | 格式、静态检查、单元测试、文档链接 | 每次合并必须通过 |
| L2 组件验证 | 协议、服务端、存储、传输、界面组件 | 修改对应组件必须通过 |
| L3 隔离端到端 | 注册、任务、结果、重连、服务恢复、审计 | 影响工作流的变更必须通过 |
| L4 受支持环境回归 | 平台矩阵、长期运行、升级/回退、资源回收 | 稳定版发布必须通过 |

测试环境限制必须在结果中显式记录。比如本地沙盒若禁止监听端口，测试状态应为“环境阻塞”，不能误记为产品测试失败或测试通过。

### 3.2 每项变更的 Definition of Done

一项整改只能在以下条件全部满足后关闭：

- 任务写明问题、范围、风险、负责人和回退方式；
- 有正向、异常和回归测试；
- 用户可见的限制同步到文档与界面；
- 变更不扩大未验证功能的默认可用范围；
- 评审记录说明兼容性影响；
- CI 结果和支持环境结果均已附到任务。

## 4. 整改路线

### M0：可信基线（第 1–2 周）

**目标：** 让团队可以准确回答“今天哪些能力能用、由什么证明”。

| 工作项 | 产出 | 验收标准 |
|---|---|---|
| 能力台账 | 版本化功能矩阵 | 每项都有状态、证据、限制、负责人 |
| 审计转任务 | P0/P1/P2 整改清单 | 每项都有验收测试与依赖关系 |
| CI 清点 | 工作流与平台矩阵 | 每个工作流有触发条件、输入、产物和失败语义 |
| 文档收口 | README 与审计口径对齐 | 不再有相互矛盾的“完成”表述 |

### M1：可靠核心工作流（第 3–8 周）

**目标：** 优先补齐已有功能的可靠工作流，不新增未经验证的能力。

| 优先级 | 工作项 | 验收标准 |
|---|---|---|
| P0 | 补齐关键链路的端到端验证 | 成功、超时、异常输入、服务恢复和资源回收均有自动化用例 |
| P0 | 统一错误模型和降级行为 | 操作员获得稳定、可行动的错误信息；日志能关联上下文 |
| P0 | 清理实验性默认路径 | 实验代码隔离、显式标记且不得作为默认发布能力 |
| P1 | 固化配置与兼容性检查 | 非法或不支持配置在构建/启动前被清晰拒绝 |
| P1 | 建立长期稳定性回归 | 支持矩阵中的环境有定期、可追溯的运行结果 |

### M2：架构与维护性（第 9–14 周）

**目标：** 避免巨型模块和隐式全局依赖继续阻碍质量提升。

| 工作项 | 方向 | 验收标准 |
|---|---|---|
| 模块边界 | 将基础运行时、业务任务、平台适配及服务端子域划清责任 | 每个模块能独立测试，依赖方向单向且被检查 |
| 重复消除 | 合并共用工具、格式化、解析与错误模型 | 同类逻辑仅有一个受维护实现 |
| 风险状态清理 | 用受控状态对象取代隐式或不安全全局状态 | 并发与生命周期有测试覆盖 |
| 接口契约 | 版本化协议、配置、存储迁移与扩展接口 | 兼容/不兼容变更均有自动化测试 |

### M3：操作体验与协作闭环（第 15–20 周）

**目标：** 在日常授权演练体验上形成可感知差异化。

- 会话、资产、任务、结果与证据形成同一时间线；
- 支持任务归属、移交、评论、审批和冲突提示；
- 审计记录不仅可保存，也能被检索、解释和导出；
- 任务和证据可映射至演练目标与报告结构；
- 扩展机制具备 manifest、版本、权限、依赖和测试样例。
- 为 UI 建立体积预算与按需加载策略；当前生产构建的主 JavaScript
  包约为 825 KB，超过构建工具的默认性能警戒线。

**验收标准：** 一次授权演练可在一个统一工作区完成初始化、协作、证据整理和报告导出，且关键操作具备完整追溯信息。

### M4：发布工程与信任（第 21–28 周）

**目标：** 稳定版可以被受控部署、验证、升级与回退。

- 建立稳定 / 实验版本通道；
- 每个构建生成依赖清单、校验信息、变更记录和支持矩阵；
- 发布前执行受支持环境回归；
- 版本升级、数据迁移和回退均有演练；
- 已知限制进入发布说明，而非隐藏在源码或历史文档中。

**验收标准：** 任意发布包都可明确回答“包含什么、支持什么、如何验证、失败如何回退”。

## 5. 基准比较方式

项目不采用“命令数量”作为与市场工具的对标指标，而以以下结果衡量：

| 结果 | Nyx 的目标 |
|---|---|
| 可靠性 | 对支持范围给出持续、可复现的回归证据 |
| 操作效率 | 减少操作者在任务交接、信息定位和报告整理上的人工步骤 |
| 协作与审计 | 每个关键动作都有清晰的操作者、理由、结果与证据 |
| 可扩展性 | 扩展有稳定接口、版本约束和兼容测试 |
| 发布透明度 | 已交付、受限和实验能力的边界公开且准确 |

这使 Nyx 可以在可审计性、现代协作体验和工程透明度上建立独立优势，而不依赖夸大尚未验证的技术能力。

## 6. 首个冲刺（立即开始）

1. 建立能力台账和审计整改任务清单。
2. 清点 CI 工作流、测试层级和受支持环境，记录真实阻塞条件。
3. 对当前未提交的传输整改完成独立评审、组件测试和提交准备。
4. 为关键端到端工作流定义最小可重复验收用例。
5. 将当前实验性、未接线和 stub 路径从“已完成”叙述中移出。

## 7. 角色与节奏

| 角色 | 首要职责 |
|---|---|
| 技术负责人 | 能力边界、架构决策、优先级和发布裁决 |
| 平台工程 | 协议、服务端、存储、兼容性与测试契约 |
| 客户端工程 | UI 协作体验、证据工作流、可访问性与报告 |
| 质量 / 发布工程 | CI、环境矩阵、回归、构建追溯与发布门禁 |
| 安全治理负责人 | 授权边界、审计、默认安全策略与风险签署 |

每周一次工程评审：只检查验收证据、阻塞和风险，不用“完成百分比”代替状态。每两周一次里程碑评审：决定继续、降级、拆分或取消某项能力。
