### Tier-B — P0 用户态（heap sleep mask，对标 CS 4.5/4.11）

**Task-B1：heap 区枚举器（3-5 天）**
- **目标:** sleep 前把 beacon 关键 heap 区注册进 `mem.rs` 的 region 表，mask 时一起 RC4
- **现状:** `mem.rs:MAX_REGIONS=8`，只注册了 32B ECDH key；`sleep.rs` Foliage 只 mask `.text`
- **设计:**
  1. `ntalloc.rs`（bump allocator）加"已分配未释放且属 beacon 自身"块链表记录（alloc 时 push，free 时标 stale 不立即摘——mask 用快照）
  2. 新 `mem.rs::enumerate_beacon_heap_regions() -> impl Iterator<Item=(ptr,len)>`：遍历 allocator 块链表，过滤掉 <64B 的碎片和已 free 的
  3. 关键区显式注册：config blob（`config.rs::load` 解密后）、token cache（`postex.rs`）、bof 输出缓冲（`bof.rs` OUT 16KiB）
  4. `MAX_REGIONS` 从 8 提到 32（heap 区多）
- **TDD 顺序:**
  1. `mem.rs` 加测试：注册 N>8 区 → 应支持（改 MAX_REGIONS）
  2. allocator 块链表单测：alloc 3 块 → 枚举返回 3 块
  3. `enumerate_beacon_heap_regions` 单测：mock allocator → 返回正确区间
  4. 集成：selftest mask 后扫 heap 找 config magic → 应找不到
- **验收:** `nyx_selftest_mem` 扩展位验证 heap 区被 mask；PE-sieve armed 扫描 sleep 期 heap 无明文 config 命中
- **参考:** [CS 4.11 sleep mask blog](https://www.cobaltstrike.com/blog/cobalt-strike-411-shh-beacon-is-sleeping)、[CS 4.5 heap 地址列表](https://hstechdocs.helpsystems.com/manuals/cobaltstrike/current/userguide/content/topics/blog_sleep-mask-update-45.htm)、[BOFRyptor](https://www.securify.nl/blog/bofryptor-encrypting-your-beacon-during-bof-execution-to-avoid-memory-scanners/)

**Task-B2：Foliage 链接入 heap mask（1-2 天，依赖 B1）**
- **动作:** `sleep.rs::foliage_helper:626` 在 mask `.text`（`:645`）的同窗口追加 `crate::mem::mask()`（data-only floor `:208` 已有调用路径，扩到 heap）
- **关键约束:** helper 线程 mask heap 时 beacon 线程必须不在读 heap——Foliage APC 已保证 beacon 在 alertable sleep，✅ 满足
- **验收:** `nyx_selftest_foliage_apc` 新增 stage 位验证 heap mask round-trip

### Tier-C — P0 内核层解锁（闭合 3 个 🔴）

**Task-C1：KslD 设备动态解析（修 R12，2-3 天）**
- **现状:** `ksld.rs:51` 字面量 `\\.\MpKsl`，真机失败
- **动作:**
  1. 用户态枚举：`QueryDosDeviceW(NULL, buf, size)` 拿全部 `\Device\` 名，匹配 `MpKsl*` 前缀（通过 `win/resolve.rs` 解析 `QueryDosDeviceW`）
  2. fallback：读注册表 `HKLM\SYSTEM\CurrentControlSet\Services` 枚举子 key，找 `ImagePath` 含 `KslD` 且有 `DeviceName`/`DisplayName` 前缀 `MpKsl` 的
  3. 找到真名后拼 `\\.\Global\\MpKslXXXX` 开设备
  4. `LivingOffDefender::open(device_name)` 改成 `open()`（内部枚举）+ 保留 `open_named(name)` 给 operator 显式指定
- **TDD:** mock `QueryDosDeviceW` 返回含 `MpKsl0a1b` 的列表 → `open()` 选对；无 MpKsl → `Err` 引导 BYOVD fallback
- **验收:** Server 2019 Defender-on 真机：`bootstrap_chain()` 走 KslD 路径（不再回退 RTCore64），记录 IOCTL round-trip；`detect.fyi Peregrine` 类工具不报新驱动加载
- **参考:** `andreisss/KslDump`（ksld.rs:17 已列）

**Task-C2：PatchGuard 运行时窗口（修 R10/R11，5-7 天，最高风险）**
- **现状:** 三套窗口全 no-op（`persistence.rs:256/351/438`）
- **选型:** kurasagi 路径（RuntimePgBypass，Win11 24H2+）—— suspend PG validation thread，长窗口
- **动作:**
  1. `PatchGuardWindow::enter_unchecked:252` 从 `Err` 改为：per-build probe PG validation thread KVA（用 `offsets.rs::probe_eprocess_offsets` 同款动态 probe 思路 + `KNOWN_PG_CONTEXT_BUILDS` 表）
  2. `RuntimePgBypassWindow::enter_unchecked:399` 实现真 suspend：通过 BYOVD/KslD driver IOCTL 调 `ZwSuspendThread(pg_thread)`（当前注释 `:426` 说 driver-side，需补 driver IOCTL 契约）
  3. `Drop:438` 实现真 resume：`ZwResumeThread(pg_thread)`
  4. `TimingRepairWindow`（Win10/Server2019 兜底）实现短窗口 repair：Drop `:351` 写回 valid_flag + 触发 repair callback
- **TDD/验证（红绿强制）:**
  1. mock：probe 返回正确 KVA
  2. 真机红绿：**回退修复 → DKOM 操作触发 BSOD（红）；恢复 → 通过（绿）**——方法见 `docs/p2-2026-06-hwbp-resolve-forwarder-postmortem.md` Phase 4
  3. 真机：`proc_hide_test.rs` 在 PG 窗口内 unlink，5 分钟（PG 周期）内多次验证不 BSOD
- **警戒:** PG 绕过是 BSOD 高危区。每改一步跑真机，不攒测。**CET-on 真机环境是瓶颈**（需 Win11 24H2+ 物理机，BIOS 开 CET）
- **参考:** [kurasagi (NeoMaster831)](https://github.com/NeoMaster831/kurasagi) Win11 24H2/25H2 runtime PG bypass PoC + PDF（product branch）

**Task-C3：repurpose ntoskrnl 全过滤（已部分在 A1，闭合）**
- A1 跳 ntoskrnl-range slot；C3 补：同时跳 KslD/WdFilter 这类"系统 protective" slot（按需，operator 配置白名单）

### Tier-D — P0 CET-safe swap（抗恶化，依赖环境）

**Task-D1：CET lenient-repair 路径（5-7 天，环境是瓶颈）**
- **现状:** `stack.rs` 无 `KiControlProtectionFault` 路径，gate=false（A0 后），CET-on 主机降级暴露栈
- **动作:**
  1. 读 [Synacktiv SSTIC 2025 PDF](https://www.synacktiv.com/sites/default/files/2025-06/sstic_windows_kernel_shadow_stack_mitigation.pdf) 定位 `KiControlProtectionFault` lenient-repair 触发条件
  2. `stack.rs` 新增 CET-aware swap 分支：`cet_active()` 真时走 lenient-repair（异常路径 + `RtlRestoreContext`），而非裸 `mov rsp`
  3. `implant-evasionsdk/swap.rs::decide` 从二元（Execute/Degrade）升级三态（Execute/Lenient/Degrade）
  4. `SPOOF_SWAP_ENABLED` 默认仍 false，operator 在 CET-on 真机验证后 arm
- **验收:** CET-on 真机（Win11 24H2 + Intel TGL+）：swap 执行无 `#CP`；xacone/K2 检测器扫 `[RSP]` 见合法 gap 地址
- **参考:** [Connor McGarr](https://connormcgarr.github.io/km-shadow-stacks/)、[sroettger CET gist](https://gist.github.com/sroettger/fe66f7eb0cb10a8ebd1454875a7131ea)

## 3. 每个 Task 的 Definition of Done

每个任务必须同时满足：
1. **代码改完** + `cargo check`（implant-win: `cargo +nightly check --target x86_64-pc-windows-gnu`；其余 `cargo test --workspace`）绿
2. **测试**：算法层单测（host）+ 真机 selftest（适用项）红绿验证
3. **文档同步**：改动的 doc 注释/docstring 与代码一致（不再出现"defaults OFF"但代码 `true` 的矛盾）
4. **capability doc 更新**：`docs/BYPASS_CAPABILITIES.md` 对应行状态更新 + 真机证据

## 4. 风险与依赖

| 风险 | 影响 | 缓解 |
|---|---|---|
| CET-on 真机不可得 | D1 卡住 | 先做 B/C，D1 标"环境依赖"长期项 |
| C2 PG 绕过 BSOD | 真机死机 | 红绿强制 + 每步独立验证 + 备份快照 |
| C1 KslD 设备名跨 Defender 版本不稳 | bootstrap 回退 RTCore64 | `open_named()` 显式指定 fallback + 真机多版本测 |
| B1 heap mask 误伤 beacon 活跃数据 | beacon 崩 | APC 窗口保证 beacon sleep，单测覆盖 |
| Tier-0 未提交叠新改动 | 调试混乱 | **A0 必须最先做** |

## 5. 不要做的事（避免无效投入）

1. **不要试图绕 NDR 行为建模**（Vectra）——无技术 bypass，只能运营（大 jitter/CDN fronting）
2. **不要在 HVCI-on 主机做 inline kernel hook**——EPT VM-exit 必 BSOD，所有内核操作限 data-section
3. **不要急着 arm `SPOOF_SWAP_ENABLED=true`**——D1 落地前 CET-on 必崩
4. **不要扩 `netsec.rs::dump_lsass` 前不做 LogonSession 偏移表**——R15 的盲读不能出凭据，硬扩只是浪费
